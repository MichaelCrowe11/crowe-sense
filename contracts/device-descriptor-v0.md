# Crowe device descriptor, v0, and the operations door

The telemetry contract (`telemetry-v1.md`) says what a node *reported*. This document
says what a node *is*: what it can measure, what it can do, which limits it enforces
and how it may be reached, as one JSON document an agent or a program reads before it
touches the device. It is served in two places, like everything else:

| where | path | auth |
|---|---|---|
| on the node | `GET /v1/describe` | none (LAN or Tailscale only) |
| on the relay | `GET /v1/nodes/{node}/describe` | `Authorization: Bearer <Crowe ID access token>` |

The node publishes it to the relay on start and daily (`POST /v1/descriptor`, signed with
the node key like a batch). The relay serves it verbatim and adds nothing.

## Where this comes from, and what it is not

The shape follows the public description of Anthropic's Model Hardware Standard
(announced 2026-08-27, research preview): a driver with `read` and `write` primitives,
devices discoverable in a common format, operator notes ("driver tags") compiled into a
reference file that lists what a device measures, what can be adjusted and which safety
limits are enforced, with those limits enforced at the driver and not in a prompt, and
reachable over MCP, a command line and code.

The MHS specification is not public as of 2026-09. Nothing here claims conformance to
it; the schema id is Crowe's own. When the specification opens, an adapter maps this
document onto it. The `standards` block in every descriptor says exactly this.

### Rules a reader can rely on

- **`measurement_range` is the maker's specified range**, given so a reader can tell a
  plausible value from a fault. It is not a safety limit and nothing enforces it.
- **A derived metric says so** (`kind: derived`, `depends_on`, `algorithm`) and always
  carries quality `est`. It is not a measurement.
- **`preferred_source`** is which driver's value the node serves when several report the
  same metric (`crowe/metrics.py`). The others are still listed under `sources`.
- **Every constraint names its enforcer** (`enforced_by`), and each enforcer has a test in
  `firmware/tests/test_operations.py` showing the refusal outside the limit. A constraint
  without code behind it does not appear here.
- **Tags are notes.** They come from `[device] tags` in `node.toml`, they appear in
  `annotations`, and they change nothing in `measurements`, `operations` or `access`. A
  tag that says "the interlock is engaged" does not create an interlock.
- **`revision`** is a hash of the document without `generated_ts` and
  `operations.executor`. Two descriptors with the same revision describe the same node
  the same way; a read of one is a read of the other.
- **`operations.executor.gpio`** is what the pin owner (the watchdog) last wrote to its
  status file, and how old that report is. `"unknown"` means the API could not read it.
  It is never inferred by the API process, which cannot see the pins.

## Operations: the one write door

```
GET  /v1/operations                    the registry, whether operations are enabled, cooldowns, recent requests
POST /v1/operations/{operation}        request one; body {"args": {...}} or {}    -> 202 with the request row
GET  /v1/operations/{request-id}       the row: status queued | running | done | rejected | expired | unknown
```

Only on the node. The relay has no such paths and never will carry a write; a cloud
client that wants to act has to reach the node directly. `access.write_path` says so.

**Authorization.** `POST` requires `Authorization: Bearer <operator token>`, the token
`crowe-provision --operations` writes to `/etc/crowe/operator.token` (mode 600). It is
checked before the body is read or the operation is named, so an unauthorized caller
learns nothing. Reachability is not authorization: a caller on the LAN still needs the
token, and so does localhost. Reads stay open on the LAN as before.

**Validation.** Unknown operations are 404 `unknown_operation`; an unknown argument or a
value outside its bound is 400 `bad_args`, refused rather than dropped. A request inside
an operation's cooldown is 429 `cooldown` with `retry_after_s`. Operations disabled in
`node.toml` answer 403 `operations_disabled` to every write.

**Execution.** The API never touches a pin. It queues the request in
`operations.sqlite`; the watchdog, the one process that owns the GPIO, claims it, checks
the cooldown again, runs it, and writes the result. Statuses:

| status | meaning |
|---|---|
| `queued` | accepted, waiting for the watchdog (normally under a second) |
| `running` | the watchdog has it |
| `done` | it ran; `result` says what happened, including `simulated: true` on a host with no GPIO in simulate mode |
| `rejected` | it did not run; `result.error` is `cooldown`, `unavailable` (no GPIO, no simulate) or `unimplemented` |
| `expired` | nobody claimed it within 60 s (the watchdog was down); it did not run |
| `unknown` | the watchdog restarted while it was running; it may or may not have happened |

`unknown` is deliberate. A hotspot reset can happen and take the network with it before
the acknowledgment leaves; a reader that cannot tell must not be told `done`.

**Audit.** Every request row keeps who asked (`X-Crowe-Operator` header, else the
caller's address), when, with what, and what came of it. `GET /v1/operations` lists the
last twenty.

## The registry, today

| operation | does | limits |
|---|---|---|
| `indicator.identify` | blinks the three status LEDs together so a person can find the node | `seconds` 1 to 30, default 10; at least 5 s between runs |
| `uplink.reset` | holds the hotspot power line for 3 s; the backhaul drops for up to a few minutes | 10 min between requested runs; also counts toward the watchdog's own automatic reset cooldown |

That is the whole writable surface of a v1 node. There are no fans, humidifiers or
valves on it, and the descriptor does not pretend otherwise. When an actuator is added,
it arrives as a registry entry with its bounds, its enforcer and its test, and the
descriptor grows by exactly that.

## Reaching it

| surface | reads | writes |
|---|---|---|
| any HTTP client | `GET /v1/describe`, `/v1/latest`, `/v1/history` | `POST /v1/operations/{id}` with the operator bearer |
| MCP (`python3 ~/crowe-sense/mcp_server.py`) | `describe_device`, `read_latest`, `read_history`, `list_operations` | `request_operation` (needs `CROWE_SENSE_OPERATOR_TOKEN`, direct source) |
| `crowe sense` | `describe`, `read`, `operations`, plus the existing `status`, `latest`, `history` | `operate <id>` (confirms first; direct source) |
| Crowe Logic desktop | the Crowe Sense plugin over the MCP server, read tools at the read-only tier | `request_operation` at the Execute tier, behind a one-shot approval the operator cannot switch off |

## Versioning

This is v0: additive changes (a new measurement, a new operation, a new annotation) do
not bump it. A renamed field or a changed meaning goes to v1 and both are served for a
release. `telemetry-v1.md` is unchanged by this document; the descriptor sits beside it.
